# Builder OS V1.5 readiness

Evidence date: 2026-08-23  
Baseline: `00f60b121e5b688f193bb23a03521e2ddc140372`  
Implementation checkpoints: `5ffae7d`, `d8c7536`

## 1. V1.5 status

**NEAR READY.** Builder OS is materially easier to operate on real creative
projects: it chooses project-specific creative work, records whether that work
actually ran, traces approved design into implementation and rendered QA,
separates human authority from mechanical effort, and preserves rejected
directions into verified continuations. The deterministic suite is green.

It is not declared fully ready because the V1.5 work did not execute a new live
external-provider journey, Cursor was unavailable, and one gate-adjacent
decision remains explicitly blocked for human authority.

## 2. Meaningful capabilities added

- Human interruptions now carry both a necessity class and an operational
  category; project status separates mechanical work, external actions and
  creative authority.
- Creative status exposes the latest evidenced strongest aspect, weakest
  aspect, highest-value improvement and iteration recommendation.
- Creative-operations readiness rejects partial implementation mappings,
  unobserved visual proof, missing drift classifications, unlinked reviews and
  unlimited automatic iteration.
- Five different real-project fixtures exercise success and non-success paths.
- A pre-G1 direction restart preserves the exact rejected `DESIGN.md`, human
  reason, inputs and parent provenance in a non-overwriting S3 child.
- Every executable skill has deterministic trigger/input/output/stop checks.

## 3. Human Intervention Budget results

The runtime now records `necessary`, `valuable`, `avoidable` and `unacceptable`
alongside `manual-setup`, `file-movement`, `prompt-discovery`,
`routine-confirmation`, `creative-decision`, `external-provider-launch` and
`review-decision`. Its normal full-run control records at least one genuine
creative decision and one external-provider action while reporting zero
avoidable interruptions, zero system-maintenance interruptions and zero
mechanical work. Legacy rows are classified and migrated when next updated.

This is a deterministic control, not a measurement of every historical run.

## 4. Creative Director Loop results

The creative-review ledger covers thesis, distinctiveness, memorability, visual
craft, interaction, narrative, fidelity, portfolio value and generic patterns.
The latest review must identify strongest, weakest, biggest risk, one
highest-value improvement, whether another iteration is worth doing, and what
must not change. A follow-up names its parent. Two unresolved automatic
iterations stop for human judgement; a linked `iteration: no` closes the loop.

The loop can report technically complete but creatively unresolved work. It
does not grant a gate and does not enter isolated S5.

## 5. Design to implementation traceability

Approved `PROJECT.md`, G1-locked `DESIGN.md`, `HANDOFF.md` and `AGENTS.md` derive
a hashed project-local ledger. Each approved requirement is mapped to an
implementation anchor and evidence. A partial or not-implemented mapping cannot
satisfy implementation readiness. Source drift invalidates stale claims.

The chain is now durable as reference evidence to design decision to approved
requirement to implementation mapping to rendered evidence to creative review.

## 6. Design drift detection

Every approved requirement needs one explicit classification: `approved`,
`allowed`, `drift` or `unknown`, anchored to observed evidence. Missing
classification remains a gap; `drift` and `unknown` remain unresolved. This
targets thesis, signature interaction, responsive transformation and hierarchy,
not harmless technical differences.

## 7. Visual QA improvements

The S4B boundary receives a project-derived, thesis-first visual-QA plan and the
canonical visual-QA method. Verified evidence requires rendered or observed
evidence plus an observed positive control; code inference and unverified
screens cannot be promoted into visual proof.

A current local rerun of the existing Signal Atlas fixture observed the working
interaction at 1280x900 and 375x812 with no narrow-width horizontal overflow.
Breakpoint inspection found the signal horizontal at 699px, vertical at 700px,
and horizontal again at 701px/768px. That confirms the already-recorded tablet
drift. Reduced-motion behaviour remains unobserved. No new screenshot artifact
was claimed or added by this pass.

## 8. Research and reference improvements

Research remains adaptive: minimal, standard or deep based on novelty,
uncertainty, reference sensitivity, genericness risk and technical complexity.
Reference records still distinguish found, inspected, inaccessible and used.
Inspected claims require a hashed retrieval or visual artifact, concrete
observations, transferable mechanisms, explicit borrow/reject decisions and a
downstream design anchor.

The Counter Archive fixture proves that two independently inspected,
conflicting references can change the recorded organising mechanism and retain
the rejected direction. It is fixture evidence, not a new live web research
journey.

## 9. Skill selection and execution improvements

All seven executable method files now declare a matching name, trigger, inputs,
output and done/stop boundary. The project ledger keeps `recommended`,
`invoked`, `completed` and `used` separate. Completion needs an evidence
artifact; use needs a downstream trace. The Kinetic Index fixture remains
blocked while mandatory selected work is unresolved, proving selection text
cannot masquerade as execution.

## 10. Provider routing improvements

Provider, model, effort, workload, split and reason remain handoff decisions;
availability and quota are checked separately. Insufficient or unknown quota
for a large handoff blocks rather than silently downgrades. A bounded unknown
provider can be a labelled assumption. Reported provider execution remains
separate from a successful structured return.

No live provider was executed in V1.5.

## 11. Handoff improvements

S4B carries the approved project context, generated operations trace, current
QA policy, QA template, selected visual-QA method and unique return template.
Each packet has canonical hashes, parent hashes, an exact project-local return
target and provider/effort guidance. Stale inputs, wrong parents and escaped
return targets fail before launch.

## 12. Recovery improvements

Partial or blocked S4B returns produce a linked same-stage child and never
overwrite the previous attempt. Missing returns pause clearly. Fresh-task
recovery discovers the single external run from the project path and refuses to
guess when histories are ambiguous.

New in V1.5, `restart-direction` archives the rejected draft and exact human
reason, records the completed-but-rejected S3 execution, keeps G1 unresolved,
and generates a verified same-stage child with the original reference, motion
and asset choices. Missing, changed or non-retry restart evidence is rejected.

## 13. Independent review improvements

S5 remains isolated to the parameterised review prompt and canonical evaluation
rubrics. It excludes `PROJECT.md`, `DESIGN.md`, `HANDOFF.md`, `AGENTS.md`,
`QA.md`, source, build history and internal creative-review evidence. The marked
judgement is preserved verbatim; the implementation provider's return cannot
become independent approval.

## 14. Social strategy improvements

Social strategy remains conditional on an explicit request. The Small Press
Launch fixture proves activation carries the user's request and cannot activate
when that evidence is removed. The existing contract requires current inspected
sources for time-sensitive claims, project-specific concepts, voice honesty,
measurement and linked revisions. It never authenticates, posts or promises
reach.

## 15. Subagent recommendation

**Limited, read-only use only; no new subagent architecture in V1.5.** The main
agent remains better for sequential, stateful creative direction and
gate-sensitive work. Two or three bounded subagents may later help compare
sources, investigate one technical question or gather visual evidence when
each has explicit inputs, output, stop condition and parent evidence.

Current official guidance says Cursor subagents use isolated context, share the
checkout by default, consume tokens independently and can overwrite concurrent
writes; it recommends starting with two or three. Cursor ACP provides a
permission-aware JSON-RPC session interface. OpenAI's current model guidance
describes multi-agent support as beta. These facts were checked on 2026-08-23:
[Cursor subagents](https://prod.cursor.com/docs/subagents),
[Cursor ACP](https://prod.cursor.com/docs/cli/acp),
[Cursor headless CLI](https://docs.cursor.com/en/cli/headless), and
[OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model).

Subagents must not route, approve gates, make material design changes, access
credentials, publish or perform the independent S5 judgement. No subagent was
run in this pass.

## 16. Additional capabilities discovered

The highest-value unplanned capability was rejected-direction continuity. It
removes a real operator reconstruction task without changing policy ownership,
routing or gates. No watcher, MCP layer, dashboard or general orchestration
framework was added because the existing controller and packet manifest were
the smaller owner.

## 18. Failure and recovery results

Deterministic controls cover unclear or ambiguous intake, unexpected existing
source, incomplete mandatory research, insufficient provider quota, partial
implementation, missing return, stale project/canonical input, wrong parent,
source drift, unobserved visual claims, missing implementation mapping, missing
drift classification, bad creative-review parentage, iteration exhaustion,
rejected direction, stale restart evidence, fresh-task ambiguity and forbidden
S5 context. Missing assets and dependencies remain explicit handoff blockers.

A genuinely poor visual result is represented as observed QA plus unresolved
creative review; the runtime can recommend iteration. Live aesthetic judgement
cannot be proven by a deterministic fixture alone.

## 19. Human-effort measurements

The runtime reports totals, counts by necessity class, counts by operational
category, pending decisions, `mechanical_work`, `external_actions` and
`creative_authority`. The full-run control reports zero mechanical work while
retaining G1 and provider launch as legitimate human work. The restart control
requires only the rejection reason; packet discovery, evidence archiving,
parenting and reconstruction are automatic.

Historical runs are not retroactively presented as though they used this
instrumentation.

## 22. Reasonably assumed

- The measured reduction in packet and restart handling should reduce operator
  effort in the next live project because the same public controller paths are
  exercised end to end in temporary workspaces.
- Small, read-only subagent tasks can help source comparison or evidence
  collection when provider availability and isolation are first confirmed.

These are not promoted to live-provider proof.

## 23. Externally unverified

- A new stranger completing the full creative journey from brief through S5.
- Cursor execution, Cursor return detection and Cursor continuation in V1.5.
- Provider quotas and behaviour outside the checked official documentation.
- macOS/Linux execution; platform paths remain simulated.
- Reduced-motion rendering in Signal Atlas.
- Social content performance and any public release installation.

## 24. Blocked

One fundamental decision is intentionally unimplemented: **should unresolved
internal creative-review readiness become a hard prerequisite for creating the
isolated S5 packet?** Current status reports the weakness, but complete return
plus mechanical QA can still prepare S5 under the existing workflow. Tightening
that boundary may change gate-adjacent progression and requires explicit human
approval.

Public publication is also blocked on a human licence decision and explicit
release authority. Cursor validation is blocked only by current availability;
Builder OS did not wait for it.

## 25. Remaining friction

- The human still opens an external implementation provider and an independent
  review session when those boundaries are required.
- A provider that cannot write its unique return target needs the documented
  temporary-file ingestion recovery.
- Visual evidence still needs an environment that can render the relevant
  states; unsupported permissions or emulation remain evidence gaps.
- Live creative quality remains judgement, not something deterministic tests
  can certify.

These are deliberate external or human boundaries, except where future provider
interfaces can safely reduce launch/return handling without weakening consent.

## 26. Recommended V1.6 milestone

After the S5 readiness decision, run one new real project through installed
V1.5 with a live implementation provider, rendered project-specific visual QA,
one internal creative-review decision, isolated S5, return recovery and fresh-
task resumption. Record real human-effort counts. Then exercise the prepared
Cursor path when available and make the public licence/release decision. Do not
add orchestration before that evidence identifies a concrete remaining task.
