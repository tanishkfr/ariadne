## Claude capability investigation — 2026-08-23

### Verified locally

- `claude` is not available on `PATH` in this Windows environment.
- No Claude command, session, authentication or provider execution was run.

### Verified from current official documentation

- The CLI supports interactive and non-interactive `-p` operation, text/JSON/
  stream-JSON output, JSON Schema output, explicit model selection, bounded
  turns and session resume.
- Claude Code uses `CLAUDE.md`, not `AGENTS.md`; a Windows-compatible
  `CLAUDE.md` may import `AGENTS.md`, but V1.5.1 will not add provider-specific
  files to projects.
- Skills are directories containing `SKILL.md` and may be installed at user or
  project scope. A thin user-scoped entry skill is therefore possible without
  duplicating canonical Builder OS policies into projects.
- Permissions can deny reads and writes, use a read-only plan mode, and combine
  permission rules with sandboxing. Bypass-permissions mode is unsafe for this
  integration and must not be used.
- Sessions persist conversation history, not filesystem state. Builder OS
  canonical files and packet evidence must remain the continuity authority.

## Architecture boundary

The experiment may add a thin reasoner contract, explicit opt-in selection,
capability detection, provider-specific entry transport, switching and failure
records. It must not change routing, gates, canonical project documents, S5
isolation, Cursor/Grok implementation routing or the existing Codex default.

The existing `adapters/claude-code.md` is a V1.5 implementation fallback. It is
not the V1.5.1 reasoner adapter and will not be removed or repurposed.

## Concrete defects found during implementation

- The old Claude implementation adapter incorrectly implied automatic
  `AGENTS.md` discovery. It now states that the verified S4B packet transports
  the project runtime state; no project `CLAUDE.md` was added.
- The first installed-runtime loader wrote Python bytecode into the immutable
  release and made its manifest stale. It was replaced before checkpointing by
  a no-cache loader; the installed-product lifecycle then passed.
- An S3 reasoner switch after a rejected direction initially risked dropping
  the restart context. Output baselines and preserved restart-source
  provenance now keep the rejected direction and human reason intact.
- The first real rollback attempt showed that a V1.5.1 launcher treated its
  additive files as mandatory in a retained 1.5.0 bundle. Runtime requirements
  are now versioned: the V1.5 core remains sufficient for V1.5, while 1.5.1
  must carry the reasoner adapter.
- The rollback exercise also exposed bytecode files appearing inside an
  immutable installed runtime. Controller/transport helper loading now disables
  bytecode writes, and installed execution is rechecked against the manifest.
- Packet source verification now tolerates CRLF/LF-only differences using the
  existing content hash while retaining raw source hashes and exact hashes for
  transcripts/parent evidence. Material text changes still fail.
