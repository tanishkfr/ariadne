# V1.4 DISTRIBUTION OPERATIONS

## Objective and rollback map

Make the established Builder OS runtime consumable as an installed product
without moving canonical ownership or weakening human gates.

```text

  -> 16273b2c7dbeb77b72065e3f8b7f4f0da122b6ff  V1.3 creative operations
  -> <V1.4 checkpoint>  distribution, tests and user documentation
```

Historical untracked validation runs were excluded from staging and never
cleaned. No destructive repository command was used.

## Prioritised findings

| Priority | Established problem | Smallest owner | Resolution |
|---|---|---|---|
| P0 | A user needed the source checkout to register `$builderos` | packaging/launcher | Self-contained Python wheel and user-local runtime |
| P0 | Managed skill pointed at a mutable checkout | installer | Versioned runtime plus generated installation record |
| P0 | Failed updates had no product-level rollback | launcher | Atomic pointer/skill swap and retained previous version |
| P1 | Setup exposed internal repository commands | product documentation | Release-first quickstart and plain first-run response |
| P1 | Repair, diagnostics and removal were manual | launcher | install repair, doctor and uninstall commands |
| P2 | Release contents and source parity were implicit | release builder/checker | Explicit allowlist, manifest, SHA-256 and negative guards |
| P2 | Existing project/runtime schema could drift | doctor | Declared compatibility range and blocking check |
| P3 | Public licence and release path were unstated | release procedure | Explicit human decision boundary and release checklist |

## Architecture decision

The chosen distribution is a `py3-none-any` launcher wheel with no runtime or
build dependencies. A custom standard-library PEP 517 backend generates the
wheel and embeds one deterministic runtime ZIP produced from the canonical
release allowlist. The launcher installs that bundle under the user's data
directory and copies only the managed Codex skill into the active skill home.

Why this is smaller than the alternatives:

- one cross-platform Python entry point replaces separate shell and PowerShell
  installers;
- no `curl | bash`, administrator write, background service or project plugin;
- no repository clone and no network request after the wheel is downloaded;
- version directories plus `current.json` provide rollback without a package
  manager inside Builder OS;
- the runtime ZIP is generated, hash-bound transport, so policies and templates
  keep their existing owners;
- update may consume one HTTPS GitHub release descriptor and exact bundle hash.

Python's packaging specification gives `[project.scripts]` the portable
console-entry role and permits a declared build backend. GitHub releases attach
versioned assets to a tag and can be made immutable. Sources inspected on
2026-08-23:

- https://packaging.python.org/en/latest/guides/creating-command-line-tools/
- https://packaging.python.org/en/latest/specifications/pyproject-toml/
- https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases
- https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases

PyPI remains deliberately disabled with `Private :: Do Not Upload`: package-name
ownership and a public licence are unresolved. npm and standalone binaries add
machinery without solving a demonstrated requirement.

## Installation state

The product separates six things:

| Layer | Owner/location |
|---|---|
| Installed product | `builderos` Python launcher |
| Runtime | immutable user-local version directory |
| Codex skill | managed copy pointing to the active runtime |
| Canonical sources | tagged Builder OS repository and generated release manifest |
| Project | user's files, decisions, QA and evidence |
| Provider adapter | runtime-owned provider-specific boundary instructions |

Install is idempotent. A healthy existing version is reused; skill drift is
repaired. Corrupt version directories are quarantined rather than trusted.
Unmanaged or user-extended skill directories block instead of being overwritten.

## Update and failure model

Remote updates require HTTPS. The release descriptor names version, artifact
and SHA-256. The archive is checked before extraction; every internal file is
checked again against `RELEASE-MANIFEST.json`. Absolute paths, parent traversal,
backslashes and symlinks are rejected.

Activation order is runtime, prepared skill, skill swap, then atomic pointer.
The previous skill is restored if the pointer write fails. A pre-pointer
interruption leaves the earlier active version intact. Rollback accepts only an
already installed runtime with valid hashes.

User configuration lives outside version directories. Projects are never an
install/update/uninstall target. Uninstall removes the runtime and managed skill;
the launcher is then removed through pip so it never tries to delete its running
process.

## Platform boundary

Windows execution is verified. The same standard-library package and path rules
were deterministically exercised for macOS and Linux, but no native macOS/Linux
machine or fresh physical laptop was used. Codex executable detection is a
warning because the desktop application may not publish a shell command.

## Validation inventory

- repository structural check, including distribution contract;
- mutation self-tests for version ownership, seed bundle, HTTPS, rollback and
  installed metadata;
- deterministic release build and source allowlist checks;
- lifecycle fixtures for install, repair, update, rollback, doctor and uninstall;
- wheel-to-clean-venv stranger test and ordinary project start;
- existing Builder OS runtime, packet, creative intelligence, creative
  operations, skill installer and validation suites;
- Python compilation and whitespace validation.

Exact final results are recorded in [V1.4-READINESS.md](../V1.4-READINESS.md).

## Decision boundary

The implementation can produce the complete release set locally. A stranger
cannot download `v1.4.0` until the owner chooses a licence, removes the private
package classifier, authorises a tag/release and publishes the generated assets.
Those are public-distribution decisions, not safe local hardening edits.
