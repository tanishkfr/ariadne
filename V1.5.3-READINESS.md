## 1. V1.5.3 status

**NEAR READY.** The installed product, optional Codex baseline, release
inventory and isolated stranger lifecycle are deterministic on Windows. It is
not yet a publishable release candidate because the public licence remains an
explicit human decision. No public release, tag, push or external fresh-Codex
test has occurred.

## 2. Codex environment changes

Fresh users now receive `$builderos` under `.agents/skills`, the current
documented personal-skill location. The general Codex baseline is separately
opt-in, generic, hash-owned, removable and absent from normal installation.
Existing global or project instructions are never merged or overwritten.

## 3. Instruction hierarchy

Official Codex documentation establishes user instructions first, followed by
project-root-to-working-directory instructions, then the current request. The
`$builderos` skill is a separate progressively loaded workflow entry point; it
is not a lower instruction file in that directory traversal. Details and dated
sources are in [CODEX-ENVIRONMENT.md](CODEX-ENVIRONMENT.md).

## 4. Builder OS and AGENTS relationship

The optional global `AGENTS.md` owns only general working defaults. Project
`AGENTS.md` remains project-owned runtime state. Canonical Builder OS policies
remain inside the immutable installed runtime and are transported only when the
skill invokes the workflow. The baseline checker rejects stage, gate, provider
or social-policy leakage.

## 5. Installation experience

A released wheel requires three public commands: install the wheel, activate
the self-contained runtime and run doctor. Activation installs the skill; no
source checkout, manual skill copy, canonical file location or packet command
is exposed. Optional baseline and Claude setup each require a separate explicit
command.

## 6. Stranger test results

An isolated Python virtual environment built and installed the wheel with no
network or source-path dependency after wheel creation. It verified version,
runtime, skill, optional baseline, doctor, repair, ordinary-language project
start, external run state, safe uninstall and project preservation. This is a
deterministic simulation, not an independent human test.

## 7. Public distribution architecture

GitHub Releases remains the smallest intended channel: one platform-neutral
launcher wheel embeds a first-install runtime ZIP; later releases publish the
same runtime ZIP plus a checksum-bound descriptor. A user-local current pointer
activates one immutable runtime, while update retains the prior version for
rollback. GitHub publication is human-owned.

## 8. Release artifact results

The builder deterministically emits the runtime ZIP, launcher wheel, release
descriptor, versioned release notes, two legacy per-artifact checksum files and
one aggregate `SHA256SUMS.txt`. The aggregate authenticates the runtime, wheel,
descriptor and notes. Exact candidate hashes are generated only from the final
clean release commit and belong to the generated inventory, not this canonical
source document. While licence selection is unresolved, the descriptor records
`publication.status: blocked` and the builder labels output a packaging
candidate instead of instructing the maintainer to publish it.

## 9. Licence status

**BLOCKED on human selection.** Repository inspection found no runtime
dependencies, vendored components, third-party code, submodules or binary
assets requiring a conflicting licence. Apache-2.0 is the technical
recommendation. Repository policy nevertheless keeps licence selection
human-owned, so `Private :: Do Not Upload` intentionally remains and no
`LICENSE` file or public-licence metadata was fabricated.

## 10. Security review

Downloads require HTTPS and descriptor-bound SHA-256. Runtime extraction
rejects absolute paths, parent traversal, backslashes and symlinks. Activation
uses verified staging, bounded atomic replacement and an immutable version
directory. The launcher does not read credentials, provider tokens, `.env` or
project content during installation. Release tests reject validation history,
operations records, transcripts, credentials and maintainer paths from runtime
output. Public GitHub security-reporting configuration remains human-owned and
unchanged.

## 11. Skill installation results

Fresh discovery selects `.agents/skills/builderos`; a recognised older managed
location is reused instead of duplicated. Source hashes, runtime path and
version are recorded. Drift, missing files, extra files and unmanaged target
directories stop or report clearly. Install, update, rollback and uninstall
retain skill/runtime parity.

## 12. Update results

The lifecycle test activates a newer verified runtime, retains the previous
one, preserves user configuration and projects, updates the managed skill, and
refreshes only an unchanged managed Codex baseline. Interrupted runtime and
pointer phases leave the earlier active version usable.

## 13. Rollback results

Rollback switches the pointer and skill to a prior verified runtime, preserves
projects and restores optional baseline parity. Existing V1.5.1 reasoner
rollback tests remain part of the complete suite. The exact V1.5.2 to V1.5.3
to V1.5.2 installed-artifact exercise passes 9/9, removes only the unchanged
newer baseline, and reads the existing project after rollback without migration.

## 14. Uninstall results

Uninstall removes the versioned runtime and managed skill, removes an unchanged
owned Codex baseline, preserves an edited baseline while relinquishing
ownership, and leaves projects and run evidence untouched. The separately
installed Python launcher remains for the package manager to remove safely.

## 26. Remaining friction

Python's portable packaging model requires a separate `builderos install`
activation command after wheel installation. Users whose existing global Codex
instructions should include the recommended defaults must merge them manually,
because Builder OS deliberately refuses unsafe automatic merging. Codex must be
restarted after instruction or skill discovery changes.

## 27. Exact human actions required to publish

1. Explicitly select the public licence; Apache-2.0 is recommended.
2. Authorise the corresponding `LICENSE` and package-metadata change.
3. Review the final clean descriptor and `SHA256SUMS.txt`.
4. Authorise tag `v1.5.3`, push of the exact release commit, and one GitHub
   release containing every generated artifact.
5. Verify the public download checksum and run one fresh external Codex task.
