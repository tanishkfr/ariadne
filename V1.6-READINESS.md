## Fixed

### Standalone stage delivery

- **Problem:** fresh sessions could be told to use a canonical file that was
  never transported.
- **Owner:** stage prompts, adapter attachment matrices and the existing packet
  generator.
- **Change:** required-input, missing-input, source-hash, parent and transition
  contracts now cover S1-S6. S3 receives only selected policy/skill inputs; S4B
  receives canonical QA inputs; S6 receives the independent judgement block.
- **Validation:** missing inputs, stale sources, wrong parents, wrong stages,
  duplicate continuations, forward transitions from blocked stages and S5
  context leakage all have mutation tests and positive controls.

### Human dependency authority

- **Problem:** a default or discovered capability could be mistaken for
  permission to install it.
- **Owner:** `LIBRARY-POLICY.md`, with G2 unchanged in `WORKFLOW.md`.
- **Change:** every exact dependency set needs human G2. The minimum-solution
  ladder tries existing, native, project-local and approved capabilities before
  current registry candidates or external discovery.
- **Validation:** dependency defaults, registry entries and generated plans are
  all rejected if they claim installation authority.

### Evidence quality

- **Problem:** source confidence and the status of the claim itself were being
  collapsed.
- **Owner:** `RESEARCH-POLICY.md` and project-local creative evidence.
- **Change:** findings separately record OBSERVED, SUPPORTED, INFERRED,
  HYPOTHESIS or ASSUMPTION. Legacy evidence remains readable without invented
  classifications.
- **Validation:** unsupported promotion, uninspected sources, missing artifacts,
  stale downstream decisions and ledger drift fail deterministically.

### Capability selection

- **Problem:** Ariadne could govern dependencies but could not compare a small
  current set of implementation capabilities without rediscovering everything.
- **Owner:** `LIBRARY-POLICY.md` remains canonical; the new
  `references/capabilities.json` is advisory transport data.
- **Change:** the registry records official source, dated revision, licence,
  acquisition, side effects and design-authority risk for a bounded set of UI
  and visualisation capabilities.
- **Validation:** fixtures cover existing capability, native implementation,
  project-local work, approved dependency, one or competing candidates,
  external discovery, stale information, aesthetic conflict and unnecessary
  dependency.

### Provider and review truthfulness

- **Problem:** provider names and downstream review work could be overstated.
- **Owner:** provider adapters, S4B handoff and S5 rubric.
- **Change:** Claude Code retains an explicit transport identity; unknown names
  are not relabelled Cursor. S4B completion excludes independent review and G3.
  S5's source-isolated frontend lens asks only what can be observed in the
  rendered result.
- **Validation:** provider identity, partial returns, isolated retry, hidden
  context injection and impossible source-review requirements have negative
  controls.

### External instruction security

- **Problem:** capability research reads repositories, documentation and tool
  output, but its data/instruction/authority split was not mechanically guarded.
- **Owner:** `PRIVACY-POLICY.md`.
- **Change:** external material may provide evidence but cannot authorise a
  command, install, disclosure, scope expansion or gate transition. Research
  skills point to the canonical policy rather than owning a parallel rule.
- **Validation:** removing human authority, trusting external instructions or
  dropping the S2/skill transport fails the existing checker.

### Distribution truthfulness

- **Problem:** the public README named maintainer-only tests, package metadata
  linked a nonexistent branch, and Python support was lower than the syntax the
  runtime uses.
- **Owner:** public documentation, package metadata and distribution checker.
- **Change:** public docs describe only shipped files and commands; changelog
  links use `master`; supported Python is 3.10 or newer; the package-name
  collision is visible before installation.
- **Validation:** release construction, aggregate checksums, source allowlists,
  Python metadata and a wheel-to-project stranger lifecycle pass.

## Convenience improvements

The operator no longer has to locate stage files, assemble packet sections,
copy canonical templates, infer parentage, choose a stale continuation, invent
return locations, reconstruct the next stage, or manually derive visual-QA
requirements from an approved direction. The controller and packet generator
perform those mechanical steps and stop only for creative authority, dependency
authority, an external-provider launch, review judgement or release authority.

## Skills

- Intake, research, reference analysis, component research, design direction,
  visual QA, creative review and social work retain explicit input/output and
  done/stop contracts.
- Reference and component work activate only when the project assessment
  selects them. A minimal project may skip both without inventing references.
- Component research now walks the minimum-solution ladder and preserves
  design authority and G2.
- Visual QA continues to require rendered/observed positive controls rather
  than accepting source inference.
- No external skill bundle was installed or copied into Ariadne.

## Capability architecture

The registry is a small extension of the existing library-governance system,
not a second dependency manager. It answers what a capability may provide and
when it merits comparison. `LIBRARY-POLICY.md` owns evaluation and G2; selected
skills own their methods; provider routing owns execution. `DESIGN.md` remains
the creative authority and may reject a technically suitable library whose
defaults conflict with the approved direction.

## Model routing and subagents

Deterministic checks run before model work. Codex remains the default reasoner;
Claude is optional and execution-unverified. Implementation provider identity
is preserved rather than inferred from a model name. Parallel read-only audits
were used for architecture, hostile product review and current resource
research because those scopes were independent; they received no gate,
dependency, release or write authority. Tightly coupled implementation remained
with the primary maintainer.

## Efficiency

The largest removed wastes are manual packet assembly, repeated canonical-file
discovery, unselected S3 skills, capability research before simpler solutions,
provider relabelling/reconstruction and reviews asked to infer hidden source.
Project artifacts and hashed ledgers remain deliberate context compression.
Independent review and human gates remain intentionally expensive because their
separation is the protection, not ceremony to optimise away.

## Human decisions remaining

1. **Python package/import identity.** PyPI already uses `ariadne` for
   [Ariadne GraphQL](https://pypi.org/project/ariadne/). The packages cannot
   coexist in one environment. Renaming only the Python distribution/module
   while retaining the product and skill name is a breaking 2.0 candidate.
2. **S0 disposition semantics.** Adding PROCEED/RESEARCH/REFRAME/PIVOT/STOP as
   enforced outcomes changes intake behaviour rather than merely hardening it.
3. **Global design heuristics.** Relaxing fixed house-style/G1 requirements in
   favour of fully project-relative tests changes canonical design policy and
   needs an explicit decision backed by real projects.
4. **Workflow boundaries.** True mode-based stage compression, changing S5's
   isolation inputs, or permitting preview-triggering pushes before G4 would
   change fundamental workflow/gate behaviour.

## Final judgement

- Ariadne is materially more capable without becoming a dependency catalogue.
- The workflow is adaptive in research and capability loading, but not fully
  compressed by project size.
- Human direction, dependency, build, ship and publish authority is preserved.
- Creative quality is better protected by evidence and rendered review, but no
  process guarantees taste.
- The architecture remains provider-neutral and maintainable because policies,
  transport data, methods and adapters retain separate ownership.
- Cursor integration is prepared, not validated.
- Windows installation/update/uninstall is credible; native macOS/Linux remains
  a simulation.
- The biggest remaining weakness is the Python package/import collision,
  followed by live real-project evidence across providers.
- I would trust the corrected candidate for private Windows validation with
  human gates and the documented package constraint. I would not recommend the
  published 1.6.0 wheel after reproducing its structured-return bypass.
