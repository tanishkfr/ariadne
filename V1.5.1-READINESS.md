Evidence date: 2026-08-23  
V1.5 rollback commit: `ff7600cf2f96a8fdf8524fc6bbe449664ffdb3ad`  
Experimental branch: `codex/v1.5.1-claude-reasoner`

## 1. V1.5 baseline commit

The recoverable V1.5 production baseline is
`ff7600cf2f96a8fdf8524fc6bbe449664ffdb3ad`. Its complete pre-change suite
passed. The experimental branch began from that commit; no historical
validation evidence was rewritten.

## 2. V1.5.1 changes

V1.5.1 adds a provider-neutral reasoner contract, explicit reasoner status and
selection, immutable switch/failure evidence, safe pre-output Codex fallback,
an optional Claude entry skill, feature-detected enable/disable commands and
layered regression fixtures. Codex stays the default and normal installation
does not enable Claude.

## 3. Reasoner architecture

Both reasoners receive the same verified stage packet and write the same
canonical Builder OS outputs. Selection lives in run metadata and operations
history, not project meaning. S1, S2, S3, S4A, S5 and S6 are reasoning
boundaries. S4B still follows `HANDOFF.md` and implementation-provider
preflight; Cursor/Grok remains the intended implementer.

No Claude-specific project document, handoff schema, workflow, policy or gate
exists. Conversation history remains disposable.

## 4. Claude capabilities actually verified

Locally verified: `claude` is absent from `PATH`; no Claude command,
authentication, model, session or file operation ran. Current official Claude
Code documentation was inspected on 2026-08-23 and documents interactive and
non-interactive CLI use, JSON/schema output, model selection, bounded turns,
permissions, skills and session resume. This proves the published interface,
not Builder OS execution through it.

The capability matrix therefore marks every Builder OS workflow capability for
Claude as `externally-unverified`.

## 5. Codex regression results

The existing Codex start, discovery, stage progression, creative evidence,
provider preflight, implementation return, independent-review isolation,
installation and project-preserving lifecycle controls remain green. Legacy
run state with no reasoner metadata resolves to Codex. Default S1 packets are
still labelled `codex`.

## 6. Claude adapter results

The adapter contract, CLI detection, blocked-unavailable state, capability
classification, packet labelling, optional skill source, managed installer and
disable path pass structural positive and mutation controls. A detected CLI is
still labelled execution-unverified until a real run completes.

No end-to-end Claude project is claimed.

## 7. Provider switching results

Deterministic runtime controls pass for Codex to Claude and Claude to Codex.
Before material output, the switch creates a linked same-stage child whose
parent is immutable `reasoner-switch` evidence. After material output, the
choice applies at the next reasoning boundary. Rejected S3 restart context is
retained across a switch.

These are structural fixtures with a simulated detected Claude CLI, not live
provider execution.

## 8. Cursor handoff parity

Both reasoners target the existing canonical `HANDOFF.md`. No alternate schema
was added. Claude reasoner selection cannot label or replace S4B: the current
Cursor/Grok route, approved design, QA inputs, unique return target and
structured return remain unchanged. A switch recorded during a partial S4B
return changes only the next reasoning boundary.

## 9. Failure and recovery results

Missing Claude at start leaves no project or run. Malformed continuity,
wrong-parent evidence, changed evidence and gate effects are rejected. A Claude
failure before material output creates a linked Codex retry. A failure after a
partial project brief/design/handoff is preserved and pauses rather than
silently replacing creative work. Neither failure nor fallback grants a gate.

Authentication failure, context exhaustion and malformed live Claude output
remain represented by the same failure record but are not locally executed.

## 10. Fallback results

The safe fallback message and behaviour are deterministic: prior state and
evidence remain, the failed packet is the parent, and Codex retries from
canonical project state only when the current output baseline is unchanged.
Codex failure does not auto-select unverified Claude.

## 11. Skill compatibility

Provider-neutral methods remain in the existing skills/policies. The optional
Claude `SKILL.md` is only an entry adapter: it locates the active runtime, uses
the controller and packet, preserves S5 isolation, stops at S4B and records
failures. It does not copy policy or create `CLAUDE.md` in projects.

Skill discovery in a live Claude installation is externally unverified.

## 12. Installation impact

Normal `builderos install` remains Codex-only and has no Claude dependency.
`builderos enable-claude` is explicit, checks for the existing CLI and installs
one managed user skill. `disable-claude` removes only that managed skill. Both
unmanaged-skill overwrite and unsafe removal are rejected.

## 13. Security impact

The integration does not read `.env`, credentials, authentication state or
provider configuration. Detection uses executable lookup and a bounded version
command only. The adapter forbids bypass-permissions mode. It does not broaden
project, push, deployment, install or publishing authority.

## 14. Performance impact

Normal Codex operation adds local JSON selection and output-baseline metadata;
it does not invoke Claude, compare providers, duplicate research or add a
runtime dependency. Claude detection occurs only for explicit Claude selection
or status checks.

Live Claude validation is blocked because Claude Code is not installed in this

## 20. Exact rollback procedure

For an installed user:

```text
python -m builderos disable-claude
python -m builderos rollback --to 1.5.0
python -m builderos doctor
```

For this source experiment, retain the branch for evidence and return to
`ff7600cf2f96a8fdf8524fc6bbe449664ffdb3ad` in a separate clean worktree or
branch. Do not delete project runs or historical evidence. No project migration
is required because legacy schema 1 remains valid and reasoner metadata is
optional.

## 21. V1.5 safety with Claude disabled

Yes. Disabling/removing the optional skill restores the normal Codex-only entry
surface. No project requires Claude, `CLAUDE.md`, a Claude package, provider
credentials or a new schema. The V1.5 baseline tests and existing projects
remain valid.
