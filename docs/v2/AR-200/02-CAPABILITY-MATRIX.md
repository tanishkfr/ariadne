# AR-200 / 02 — CAPABILITY MATRIX

Scope: Ariadne public v1.6.7, maintainer v1.6.7 (identical engine, extra verification assets), Boreal's application-native engine (read-only), and the proposed v2 actions.

## B. Detailed entries (where a decision needs justification)

### 1. Task/run lifecycle — KEEP, with one extraction
Ariadne's stage chain (S1→S2→S3→S4A→S4B→S5→S6) is genuinely enforced: `infer_next_stage` (`ariadne.py:3481-3536`) and `prepare_next` refuse illegal jumps, `load_parent` enforces allowed parent stages and retry rules (`prepare-stage.py:1306-1345`), and S5 cannot be prepared without a *passed* independent validation plus a complete return (`prepare-stage.py:1330-1344`). TEST_VERIFIED (`lifecycle.g1-locked-prepares-s4a`, `lifecycle.s4b-requires-cleared-preflight`, `lifecycle.s5-isolation`).
Boreal's contribution is a single choke point (`engine.py:321-335` → `model.assert_transition`) with an explicit transition table (`model.py:59-69`) — a cleaner pattern to adopt than Ariadne's four scattered gate re-derivations. Justification for adopting it: it is small, pure, and its absence is the direct cause of confirmed defect 2 (§01 §7). **KEEP Ariadne's semantics, EXTRACT Boreal's single-choke-point transitions.**

### 3. Context compilation — KEEP + HARDEN
Nothing in Boreal exceeds Ariadne's packet compiler; Boreal's `conversation.py` bound (5 items / 18 messages / 4 000 chars) is a *different* problem (chat continuity, not stage context) and is not a replacement. The hardening targets are measurable, not speculative: (a) S3 delivers 39 KB with no dedup between `DESIGN-TASTE.md` and `skills/design-direction.md` (both delivered; overlap not measured — INFERRED); (b) the packet is re-verified by re-hashing every source on *every* CLI call (`verify_packet`), which is O(all sources) per command (see 07-RISKS); (c) `manifest["omitted_conditionals"]` exists but no consumer surfaces it to the operator. **HARDEN**: content-addressed source cache, packet-level verification memo, and an operator-visible omission report.

### 4. Capability routing — EXTRACT + HARDEN
Two distinct mechanisms exist and only one is real:
- *Recommendation* (Ariadne): `recommend_task_routing` computes capability class, model family, effort, session strategy from nine inputs with 25 boundary tests. It is a judgement aid; nothing enforces it (`route` is a print-only command).
- *Verification* (Boreal): requested model is snapshotted into the run; the runtime-reported model is read back from the session record and compared; mismatch is recorded as `model_mismatch` and `model_verified=False`; unavailable models are refused *before* durable state is created.
**EXTRACT the identity-verification pattern** (requested vs observed, with an explicit "no comparable report ⇒ not verified" rule) because Ariadne currently ingests provider/model from the worker's own return text (`ariadne.py:2237-2301`) — a self-report with no cross-check. **HARDEN routing into enforcement** by making the capability matrix load-bearing (e.g. a design stage may not run on a provider whose `design-direction` capability is `externally-unverified` without an explicit human override recorded as an intervention). Justification: the matrix already exists, is validated, and is currently dead data.

### 6. Independent validation — KEEP + EXTRACT
Ariadne executes and hashes real commands; Boreal binds validation to a *fingerprint pair* (`baseline` vs `post_worker`) and refuses if the workspace changed, which closes a gap Ariadne has: its scope check re-reads git state at validation time and compares to the packet baseline, but there is no engine-level "the bytes I validated are the bytes that were produced" fingerprint. Both are cheap; combining them removes a class of race. Evidence: `ariadne.py:2445-2546` (snapshot compare) vs `validator.py:52-135` + `engine.py:1220-1243` (fingerprint equality). **KEEP the command execution, EXTRACT the fingerprint model.**

### 7. Independent review — REDESIGN (proven defect)
Confirmed by execution: the only enforced difference between an "independent" review and a non-independent one is the literal string `**Reviewed independently:** yes`; the reviewer's identity, session, or context isolation is never evidenced, and the same actor that produced the build can write both the review and the attestation. Boreal's engine is *more* honest (it labels the record `asserted-review-verdict` and stores `identity: "asserted-by-caller-not-verified"`) but no more verified. v2 must bind the verdict to evidence: a review transcript/provenance record produced outside the build workspace, a reviewer identity distinct from the worker identity, and a packet that is *provably* the isolated pair (Ariadne already proves this part at S5). **REDESIGN**: verdict carries `reviewer_identity`, `review_session_evidence`, and `context_digest` — the digest of the delivered S5 packet — and independence is checked against the worker identity recorded in the run state.

### 8. Authorization / human gates — REDESIGN using Boreal's binding
Confirmed defect: G1 was granted by writing two document fields and one CLI call, and the runtime then recorded the *human* creative decision as resolved. Boreal's model is strictly better in three ways and worth copying: approvals are first-class records (`approval_id`, `kind`, `subject{type,id,revision,hash}`, `source`, `identity`, `note`); the subject is a *revision fingerprint* so any edit invalidates the approval (`authorization_status` → `missing|stale|satisfied`); and privileged operations are refused unless the current fingerprint matches. Boreal still labels its own approvals `asserted-by-caller-not-verified`, and its identity channel is a token file readable by the same user — so this is *better binding*, not cryptographic proof. v2 must therefore separate: (a) approval **binding** (fingerprint, adopt), (b) approval **identity** (out-of-band record: a token-gated approval file plus an append-only approval log, and a CLI that a human runs, never the worker), and (c) **process isolation** (job objects/containers — explicitly out of scope for v2; see 07-RISKS). Do not claim sandboxing from approval dialogs.

### 9/10. Transactions and rollback — EXTRACT
Neither Ariadne nor the public product has any transaction layer: the worker edits the project and Ariadne can only *detect* violations post-hoc. Boreal's `transactions.py` is the most valuable single artifact found in this audit: propose only from a validated run, per-path scope/immutability/sensitivity re-checks, before/after content blobs, `journal.jsonl` written **before** each mutation, `tx_hash` bound to approval, per-file conflict detection at apply *and* rollback, `partial-apply`/`partial-rollback` as first-class states, and conflict preservation that never clobbers user edits. Its stated limitation is honest: multi-file writes are not atomic. Extraction complexity is moderate: `transactions.py` imports only `store` (private helpers `_ariadne_data_homes`, `write_json`) and calls `git rev-parse HEAD`. **EXTRACT** with a small `StateStore` protocol replacing the Boreal store, keeping the journal and conflict semantics verbatim.

### 11. Failure recovery — HARDEN
Ariadne classifies failures well (blocked vs routine, escalation-required, bounded repairs — TEST_VERIFIED) but has no recovery for its own interruption: if a CLI call dies between writing `packet.txt` and `ariadne-run.json`, the run has an orphan packet that `current_packet` cannot see, and there is no repair command. Boreal's `recover()` resolves interrupted transaction states from destination bytes only, never assuming success. **HARDEN**: add a `recover` path for packet/state divergence plus reuse of the journal pattern for state writes.

### 14. Persistence — HARDEN
Both systems: versioned JSON on disk, no inter-process lock (both document this), append-only logs for events. Ariadne's weakness is the hard schema gate with no migration; Boreal's weakness is the same (`schema_version != 1` → refuse). Evidence: `ariadne.py:269-270`; `store.py:105-106`. **HARDEN**: introduce an explicit, recorded, non-destructive migration path and a `readable_schemas` range in the release manifest (which already has a `project_state_schema` range but the runtime never consults it when loading state — only `doctor --project` does, `cli.py:946-967`).

### 16/17/18/19. Design intelligence — see 05-DESIGN-INTELLIGENCE.md
Summary: KEEP the two ledgers (they are real, strict and hash-bound); HARDEN the capability registry (no freshness enforcement, no licence/version verification, no ranking — and its `install_authority` string is enforced by a documentation check, not by code); EXTRACT Boreal's reference-retrieval adapter as an **opt-in, consent-gated** component (HTTPS-only, robots, byte caps, content-type allowlist, digest-verified excerpts, project content forbidden in requests); ADD a rendered-QA instrument because *no capture or inspection code exists anywhere* in either system — the `rendered == true` JSON flag in Boreal is written by the worker under test, which is not evidence.

### 20/21. API and CLI — ADD (API), KEEP (CLI)
Ariadne's only interface is `scripts/ariadne.py` with 26 subcommands and exit codes 0/1/2 (TEST_VERIFIED across the lifecycle cases). No importable API, no supported typed contracts. Boreal has a JSON-RPC coordinator but it is application-internal and protocol-bound (`coordinator/protocol.py`). **ADD** a small Python API surface (`ariadne.api`) whose functions are exactly the existing deterministic operations, so the CLI and any future Boreal adapter are both thin clients. Do not promise stability before compatibility testing (see 07-RISKS).

### 22. Distribution — HARDEN, defer rename
Verified working: offline stdlib build, embedded seed runtime, sha256-verified manifest with a version-graded required-file set, atomic skill swap, rollback, doctor, uninstall guards (TEST_VERIFIED: 55/55 lifecycle cases, 18/18 release-bundle cases, 7/7 manifest mutations rejected). Verified defects: no signature, no TLS pinning, no descriptor↔manifest version equality check, unbounded download buffering, artifact host unconstrained, and the `ariadne` name collides with an unrelated PyPI project (documented but unmitigated). **HARDEN** the integrity checks now; **DEFER** the rename (it is a breaking change with an installed-base migration; it must not be bundled into AR-201).
