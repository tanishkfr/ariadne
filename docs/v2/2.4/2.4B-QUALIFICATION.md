## B1 �?" Adaptive routing

### Registry

`src/ariadne_engine/model_evidence.py` implements:

- provider/model/revision/adapter/role/family capability records;
- `DECLARED`, `DIRECTLY_OBSERVED`, `OBSERVED_QUALIFIED`,
  `BENCHMARK_QUALIFIED`, `UNAVAILABLE`, `STALE`, `UNKNOWN`;
- sample size, measurement period, validated/failed/accepted counts, measured
  latency/tokens where supplied, evidence references and limitations;
- 30-day freshness and revision-drift invalidation;
- automatic derivation from `measurement` records plus explicit benchmark
  observation recording;
- human promotion requiring benchmark qualification, current evidence and at
  least 8 samples.

### Routing changes

- Existing `routing.route` remains authoritative.
- `routing.evidence_advice` records a shadow recommendation and always sets
  `controls_execution: false`.
- `task_execution.select_adapter` accepts an evidence ranking only from the
  caller; it never adds an adapter, drops an exclusion, or overrides an explicit
  request.
- The `apply_qualified` path is dormant without a recorded human promotion and a
  benchmark-qualified record.

### Fallback behaviour

| Condition | Behaviour |
|---|---|
| Provider unavailable | A fresh qualified alternative may be **advised**; the baseline route is kept unless the promotion gate is satisfied |
| Quota failure | Recorded as a provider failure when the runtime recorded it; no token/cost figure is invented |
| Repeated validation failure | May justify a qualified alternative; advisory only |
| Missing capability | Named blocker; no unsupported route |
| Unknown identity | No qualification |
| Stale data | No recommendation |
| No authorized provider | `NO_AUTHORIZED_PROVIDER`; nothing is invented |
| Independent review | Implementer adapter/provider/model excluded |

### Shadow comparison

## B2 �?" Context intelligence

### Changes

- `context.decide` records `revision_hash`, `reduction` and measured
  `included_bytes` / `omitted_bytes`.
- `context.stale_problems` / `require_current` refuse a moved revision or packet
  digest.
- `context_reduction=adaptive` omits an unchanged optional scope file the request
  does not name; the contract, request, mandatory methods and required policy are
  never omitted.
- `continuation.build` projects the objective, scope, validated revision,
  modified files, lifecycle, validation rows, latest failures, unresolved review
  findings, human decisions and evidence references; it refuses another revision.
- `scripts/prepare-stage.py` records delivered source bytes so the measurement is
  file-size based, not estimated.

### Before/after

Two identical disposable projects, six unchanged helper files, same request and
validation:

```text
off       packet 63,812 bytes, 20 included sources, 0 omitted
adaptive  packet 35,591 bytes, 14 included sources, 6 omitted
saved     28,221 bytes (44.2%)
```

The contract, request and mandatory methods remained in both packets. The six
omitted files remained readable in place inside the permitted scope.

### Cache measurements

8 local source-hash cache hits and 4 invalidations in the shared deterministic
run. A changed source is a miss with an observable invalidation; no stale hash
was reused. Provider prompt-cache behavior is `UNKNOWN`.

### Verification impact

The deterministic suites are green after the change. A live task was not run with
adaptive reduction; the two live samples used the default `off` profile. The
context benefit is fixture-bound and measured in bytes.

### Independent audit

An independent read-only verifier inspected the diff from `3ec1efc` to the
qualification commit, re-ran the 2.4B, engine-core, 2.4A, release and repository
checks, re-ran the release benchmark (97/97), verified the live logs and the
recorded full-benchmark artifacts, and searched for gate bypass, review
weakening, registry rewrite, network/background code and fabricated metrics.

**Verdict: PASS for the release-candidate qualification; no critical or high
findings.** The verifier confirmed the candidate's own PARTIAL verdict on live
routing efficiency is a stated limitation, not a mismatch. Two medium findings
were raised and were closed in the final commit:

1. a qualified alternative with as many failures as passes could be recommended;
   alternatives now require a positive validated margin (`_candidate_healthy`);
2. a promotion did not expire when its evidence changed; `promoted_scope` now
   compares the recorded registry digest against the current one, and a new
   observation invalidates the promotion.

Both are covered by new cases in `scripts/test-ar24b.py`; the mutation suite was
re-run (12/12 killed). The verifier did not execute `test-wheel-install.py`, the
baseline shared-case rerun, or the live Codex/Claude/Cursor cases; those remain
recorded-only or explicitly unexecuted as stated above.

## Outstanding

- **Unresolved:** no live benchmark-qualified model record exists, so
  `OBSERVED_QUALIFIED`/`BENCHMARK_QUALIFIED` routing has not been validated
  against real provider outcomes.
- **Environment blocker:** Claude Code is installed but unauthenticated; Cursor
  is absent; Codex was not run; the baseline release-subset rerun timed out at
  the harness bound and was not counted.
- **Unexecuted tests:** live adapter cases for Codex/Claude/Cursor, live adaptive
  context, and any multi-trial live model comparison.
- **Unverified claims:** no token saving, provider cache saving, model ranking,
  cost reduction, or live routing improvement.
- **Deferred capabilities:** automatic promotion (deliberately absent), external
  skill marketplace (out of scope), provider quota discovery (no supported
  interface), cross-project memory (unchanged and still private by default).
- **Local migration note:** a promotion recorded before the audit fix carries the
  old digest formula (which included a clock-derived age) and will fail closed
  after upgrade. That is intentional; re-record the promotion after re-checking
  the current evidence. No tracked approval or gate is affected.

## Recommendation

- **Is 2.4B complete?** The engineering scope is complete for a candidate; live
  routing efficiency is not proven.
- **Is it materially better than 2.4A-R?** It is materially better on measured
  context size (44.2% on a six-file fixture), measurement coverage, stale-evidence
  refusal, continuation safety and skill attribution. It is not yet better on a
  measured live model outcome.
- **Proceed to 2.4C?** Only after a live, same-workload routing evaluation, or
  proceed with 2.4C treating routing as shadow-only.
- **Another hardening pass?** Not for correctness. One focused live evaluation
  pass is the missing evidence.
- **Exact next action:** run the same 8-task routing benchmark on at least two
  authenticated providers with recorded model identity and usage, then decide
  whether any route is eligible for a human promotion. No route should change
  before that.
