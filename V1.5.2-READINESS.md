## 1. V1.5.2 status

**NEAR READY.** The optional social-intelligence path is structurally complete,
project-grounded, provider-neutral and covered by realistic positive and
negative fixtures. No live platform post, live analytics return or Claude
session was executed, so production usefulness remains externally unverified.
V1.5/V1.5.1 behaviour continues to pass deterministic regression checks.

## 2. Social capability architecture

The existing `social-strategy` method remains the method owner.
`SOCIAL-STRATEGY.md` carries the user-facing plan,
`CONTENT-LEARNINGS.md` remains the human-readable learning owner, and
`.builderos/creative-operations.json` stores artifact hashes, revisions,
results and continuity. No workflow stage, gate, policy, platform connector,
scheduler, database or social-specific provider format was introduced.

## 3. User experience

A person can ask for launch, distribution, content planning, post ideas or
performance analysis in ordinary language. The managed entry skill inspects
the latest project evidence, activates the optional method when required and
returns five plain sections: recommendation, reason, posts, tests, and the
smallest remaining user input. Internal event names remain recovery details.

## 4. Platform research

Builder OS embeds no supposedly timeless algorithm advice. A run selects
minimal, standard or deep research according to the actual decision. Current
format, discovery, feature, licence and analytics claims need inspected source
artifacts and access dates; time-sensitive evidence older than 180 days fails
as current evidence. Fixture pages prove the contract, not live platform facts.

## 5. Source quality

Source-backed recommendations classify official platform material, creator
guidance, primary research, credible industry research or observed examples.
Every meaningful row connects SOURCE -> FINDING -> DECISION and carries one of
documented, observed, researched, inferred or speculative. Found,
inaccessible, outdated and inspected sources remain different states.

## 6. Skill selection and execution

Social remains off without an explicit request. A late request can reactivate
an optional method previously skipped at intake while preserving that earlier
history. Recommended, invoked, completed and used still need separate evidence;
the realistic flow exercises the complete state chain.

## 7. Content generation

A strategy contains three to six platform-specific treatments rather than a
bulk content calendar. Each treatment records its purpose, format, hook,
complete draft, visual, CTA or `none`, evidence basis and falsifiable
hypothesis. Generic announcements, engagement bait and performance promises
are rejected deterministically.

## 8. Voice handling

Voice matching requires at least two hashed writing examples supplied for the
project. Without them, drafts are explicitly rough and use concrete project
language without claiming imitation. No personal corpus is copied into global
Builder OS state.

## 9. Visual content handling

Every plan inventories visual material as `existing`, `to-create` or `missing`.
Existing assets need readable artifact paths and hashes. Missing material
cannot masquerade as a screenshot or recording; the plan instead states the
specific asset work required.

## 10. Experiment design

Each post treatment contains a hypothesis, measure and one changing variable.
Cadence derives from owner capacity and available content, not a universal
posting-frequency claim. Inconclusive remains a valid and expected outcome.

## 11. Performance learning

`social-result` accepts only user-provided, artifact-backed metrics or
qualitative observations. `social-learning` records PLAN -> RESULT ->
INTERPRETATION -> NEXT TEST. One result cannot support or contradict a pattern;
a promoted rule needs three distinct recorded posts.

## 12. Social memory

Strategies, result corrections, learning revisions and source/asset hashes stay
inside the project. A fresh task reloads that ledger rather than relying on
conversation memory. Corrected metrics preserve the original record and make
dependent learning explicitly stale until revised.

## 13. Provider compatibility

Codex uses the installed shared method and is structurally verified. The
optional Claude entry points at the same skill, templates and event schema;
Claude execution remains externally unverified because its CLI is unavailable.
Cursor/Grok remains the implementation route and receives no social role.

## 14. Human intervention results

Routine project inspection, source trace, platform comparison, drafting,
hypothesis structure and result analysis require no gate approval. The owner
still supplies private voice examples when desired, confirms sensitive claims,
provides performance evidence and approves every publication through G5.

## 15. Realistic fixture results

Five fixtures cover a portfolio launch, an interactive experiment, a
process-led case study, weak visual assets and a launch with synthetic but
realistic owner-supplied performance data. All exercise bounded platform
selection, project story, visual status, content treatments and fresh-task
continuity. Targeted social controls pass 59/59.

## 16. Failure and recovery results

Negative cases stop unsupported audience assumptions, thin project stories,
omitted visual status, unresolved source conflict, outdated and inaccessible
evidence, URL-only research claims, false voice matching, generic copy,
guaranteed reach, provider-generated metrics, unknown metrics, empty results,
silent correction and one-post overgeneralisation. Cross-version packet
verification also distinguishes harmless checkout line-ending differences
from changed canonical content and changed delivered packet sections.

## 22. Remaining friction

The reasoner still performs live browsing and writes the strategy artifact; the
controller verifies evidence but does not fetch platform sources itself. Voice
examples and analytics must be deliberately supplied. These are appropriate
privacy and truth boundaries rather than candidates for silent automation.

## 23. Future integration recommendations

Keep platform APIs, schedulers, account analytics and publishing outside the
core. If real-project evidence later justifies an integration, add it behind an
explicit permissioned adapter that produces the same user-provided-result
contract. Do not store credentials in projects or weaken per-post G5 approval.

## 24. Recommended V1.5.3 or V1.6 milestone

Run one finished real project through current-source research, owner review and
manual publication; return two or more authentic result artifacts over time.
Use that evidence to evaluate recommendation usefulness, voice fit, metric
normalisation and whether any read-only analytics adapter earns its cost.
